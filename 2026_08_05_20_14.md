## 1. Executive Verdict

# **GO_WITH_REVISIONS**

应继续启动一个**独立于原 RAVEN-M 方法主张的多系统复现与过程诊断项目**。该项目的科学价值不在于为 RAVEN-M 寻找新名字，也不在于证明某个现成模块具有新颖性，而在于回答以下三个更基础的问题：

1. 现代公开 mobile-GUI systems 中，是否有系统能够在同一批 19 个 AndroidWorld Hard task classes 上逃离旧实验的近零成功率 floor；
2. 即使 official task success 仍为零，不同系统是否在 exact-action loops、action-effect verification、feedback-to-policy binding、wrong-target selection 和 finish authority 等预先冻结的过程指标上表现出可复现差异；
3. 旧 RAVEN-M 失败究竟主要来自共享的 controller/grounding floor，还是部分现代系统已通过更强模型、不同 observation privileges、不同 action space 或不同 controller package 跨过该 floor。

本授权**不撤销**以下冻结结论：

- RAVEN-M 作为新 memory method：`STOP_RESEARCH_METHOD`；
- EEST-AC：停止；
- reminder timing / Correct Memory Wrong Target：停止；
- Destination-First Binding Gate：不得实现；
- generic memory、generic critic、generic verifier、generic loop breaker：不得作为新的方法贡献。

多系统 benchmark 可以产生新的**比较证据和 qualification evidence**，但不得把 native-system 间的性能差异直接归因于 framework design。更强 backbone、UI tree/accessibility privilege、外部工具、不同 action grammar、不同 prompts、更多 calls 和更大 token budgets 都必须单独披露。

本协议作出六项关键修订：

1. **加入 RAVEN-B3。** 它在 r56 中达到 4/4，而 M0 为 3/4，是现有最强简单基线，不能继续只比较 B0 与 M0。
2. **加入 UI-Voyager。** 它具有公开 checkpoint、MIT license、官方 AndroidWorld runner 和直接 vLLM 部署路径，是原候选池遗漏的最强可快速运行系统之一。
3. **将 M3A 移出 screenshot-only 公平 lane。** M3A 使用 screenshot、标注图和 UI-element/structured information，必须进入 structured-observation lane。
4. **首轮排除 ColorMobileAgent、DroidRun、UI-TARS-1.5、VLAA-GUI、K2-Agent、VeriGUI 和 BacktrackAgent。** 排除原因分别是 checkpoint/config 未完整冻结、privileged observations、缺少已核验 AndroidWorld runner，或本质上只是 mechanism prior。
5. **任何主结果都不得称为 exact official reproduction。** 固定 19-task Hard subset、统一 step budgets、不同硬件和本地 adapter 已经使它们至多属于 configuration-equivalent reproduction。
6. **S3 expansion 完全由完整性和可比性决定，不由 S2 成功率决定。** 零成功不能阻止确认阶段，正成功也不能自动扩大候选池。

### 2.2 旧 Hard 结果对新协议的约束

旧 breadth experiment 共 95 cells：

- 15/95 因 action contract 缺少 `answer` 而结构性不支持；
- 剩余 80 supported cells 中：
  - 1 success；
  - 50 budget exhaustion；
  - 14 model-declared infeasible；
  - 14 premature finish；
  - 1 invalid after repair；
- B3 与 M0 在 direct 19-task comparison 中均为 0/19；
- M0 相对 B3 增加约 33% model calls、53% tokens 和 52% wall time；
- 477 个 executed actions 没有 screenshot change；
- 59/80 cells 存在三连 exact-action repetition；
- 32/80 cells 存在十连 repetition。

这些结果意味着：

1. official success 仍必须是 primary outcome；
2. 但只报告 success 会浪费绝大部分信息；
3. `answer` contract 必须在 Hard calls 之前离线验证；
4. loops、no-effect actions、feedback non-binding 和 evaluator-rejected finish claims 必须成为冻结 process metrics；
5. 新 benchmark 不能把 arm activation、reflection calls 或 memory citations 当作 utility。

### 2.3 r56 与 timing 结果的边界

r56 中 B3 为 4/4、M0 为 3/4，M0 多使用 69.53% prompt tokens。该结果证明 B3 是必须保留的强简单 baseline，但它是 protocol-engineering suite，不是 AndroidWorld Hard efficacy estimate。

Timing v0.1–v0.3 共 96 cells、192 Qwen calls：

- 0 parser failures；
- 100% exact-value recall；
- Early/Late token matching；
- 三轮 Timing × Ambiguity interaction 均为 0；
- 全部 development-contaminated；
- 0 live Android actions。

新 benchmark 只可以使用这些结果定义 process annotation categories，不得继续 timing intervention 或把这些 cells 加入新统计。

## 3. Frozen Reproduction Taxonomy

每一个 arm 必须且只能被赋予以下一种标签。

### 3.1 `EXACT_OFFICIAL_REPRODUCTION`

必须同时满足：

- official repository 与 exact commit；
- exact checkpoint revision；
- official prompt；
- official observation channels；
- official action grammar；
- official model provider/runtime；
- official benchmark version；
- official full task distribution；
- official step and retry budgets；
- official evaluator。

**本协议主表中没有任何 arm 属于该类别。**

19-task Hard subset、统一 budgets、单 Windows host 和本地 logging adapter 已经使 exact reproduction 不成立。

### 3.2 `CONFIGURATION_EQUIVALENT_REPRODUCTION`

允许的差异仅限于：

- 固定为本项目 19-task Hard subset；
- 环境 adapter；
- normalized logger；
- 本协议统一的 action、call、token 和 wall-clock ceilings；
- 相同 checkpoint 和 official controller semantics。

适用：

- GUI-Owl-1.5；
- Mobile-Agent-v3.5；
- ScaleCUA；
- UI-Voyager。

允许表述：

> “使用官方代码、公开 checkpoint 和冻结的本地 AndroidWorld configuration 进行 configuration-equivalent reproduction。”

禁止表述：

> “完全复现了论文 AndroidWorld headline result。”

### 3.3 `COMMON_BACKBONE_ADAPTER_COMPARISON`

固定相同 Qwen checkpoint、processor、decoding、screenshot resolution 和最大资源 envelope，比较 controller package。

适用：

- RAVEN-B0；
- RAVEN-B3；
- RAVEN-M0；
- MobileUse MultiAgent；
- M3A-Qwen，但 M3A 因 structured observation 单独成 lane。

该类别允许比较**完整 controller packages**，不允许把差异归因于某个单一 memory、planner、reflection 或 critic module。

### 3.4 `MECHANISM_PORT`

只把论文机制移植到新系统，例如：

- VLAA-GUI loop breaker → AndroidWorld；
- VeriGUI TVAE → RAVEN controller；
- BacktrackAgent recovery → Qwen controller。

**本阶段不执行任何 mechanism port。**

### 3.5 `PAPER_ONLY_REPORTED_REFERENCE`

满足以下任一条件：

- 没有完整 runner；
- 没有 checkpoint；
- 没有 license；
- 只发布 trajectories；
- 需要未公开 proprietary model；
- 需要与本环境不兼容的 privileged tools；
- 无法在 bounded S0 内冻结。

这些系统可出现在 literature/reference table 中，但不能出现在 scored arm table。

## 8. Exact Budget, Reset, Retry and Randomization Rules

### 8.1 Environment actions

每一个实际作用于 Android environment 的命令均计 1 action，包括：

- tap/click；
- swipe；
- type；
- press back/home/enter；
- launch app；
- wait；
- `answer`；
- finish/terminate action，若它经过环境 action interface。

Controller 内部 reasoning、summary、reflection、memory 和 verifier calls 不计 environment action，但计 model calls 和 tokens。

达到 \(B_t\) 后：

- 禁止执行第 \(B_t+1\) 个 action；
- official evaluator 仍调用一次；
- outcome 为 budget-exhausted task failure。

### 8.2 Model-call ceiling

每 cell 的 total model calls，包括所有角色、repair、reflection 和 internal retries：

\[
C_t=\min(4B_t,240).
\]

超过时立即停止该 cell，调用 evaluator，记录：

```text
termination_reason=model_call_ceiling
```

### 8.3 Token ceilings

按每个 arm 自己的 exact tokenizer 计数：

\[
I_t=\min(20{,}000B_t,\ 1{,}000{,}000)
\]

为 input-token ceiling；

\[
O_t=\min(2{,}048B_t,\ 131{,}072)
\]

为 output-token ceiling。

不同 tokenizer 的 token totals 不可直接作为模型能力比较，只能作为该 arm 的 cost metric。

### 8.4 Wall-clock ceiling

每 cell：

\[
W_t=
\max
\left(
30\text{ min},
\min(120\text{ min},90B_t\text{ sec})
\right).
\]

计时包含：

- controller inference；
- environment actions；
- post-action waits；
- internal retries；
- evaluator call。

不包含：

- checkpoint 首次下载；
- model server boot；
- scheduled environment cold boot。

这些 setup costs 单独报告。

### 8.5 Reset lifecycle

每 cell 精确执行：

1. 验证 emulator/device identity；
2. 验证 AndroidWorld commit 和 task class；
3. 设置 task seed；
4. initialize task；
5. 等待 UI stabilization；
6. 保存 initial screenshot hash、task-parameter hash；
7. 运行 controller；
8. official evaluator 恰好调用一次；
9. 保存 raw reward/evaluator output；
10. task teardown；
11. official lifecycle reset；
12. 验证下一 cell 无残留 app/task state。

在第一 model call 之前若 reset 失败：

- 允许一次完整 reset；
- 第二次失败则该 cell 为 `INFRA_INVALID`。

每完成 10 个 scored cells、发生 emulator crash 或连续出现 2 个 reset warnings 时，执行 cold emulator reboot。

### 8.6 Rerun policy

| 情况 | 是否重跑 |
|---|---|
| 官方 evaluator 返回 0 | 否 |
| 错 target、loop、no effect、premature finish | 否 |
| 模型输出不符合 official grammar，且 official repair 已耗尽 | 否；计 scientific failure |
| 模型声明 infeasible | 否 |
| model-service connection 在生成前中断 | 允许 1 次 infrastructure rerun |
| emulator crash、ADB disconnect、reset corruption | 允许 1 次 infrastructure rerun |
| logger 丢失关键 raw artifact | 允许 1 次 infrastructure rerun |
| 同一 cell 第二次 infrastructure failure | 不再重跑 |
| task-specific adapter bug 在 Hard call 后发现 | 不得修复并继续；触发 protocol stop |

所有 reruns 必须：

- 使用相同 task-parameter hash；
- 使用相同 model seed；
- 使用相同 prompts/configs；
- 保留原失败 attempt；
- 用 `rerun_of` 明确链接。

### 8.7 Invalid-output classification

```yaml
SCIENTIFIC_VALID_SUCCESS:
  official_evaluator: 1

SCIENTIFIC_VALID_FAILURE:
  official_evaluator: 0
  environment_and_logger_valid: true

MODEL_INVALID_SCIENTIFIC_FAILURE:
  parser_failed_after_frozen_official_repair: true

INFRA_INVALID:
  examples:
    - emulator_crash
    - model_service_disconnect
    - task_reset_failure
    - logging_corruption
    - adapter_exception_not_caused_by_model_output

CONTRACT_INVALID:
  examples:
    - answer_action_missing_after_S0_pass
    - action_coordinates_systematically_mis-scaled
    - evaluator_state_exposed_to_agent
```

`MODEL_INVALID` 属于模型/系统表现，不能从 denominator 删除。

### 8.8 Randomization and execution order

由于只有一台 Android host，live episodes 严格串行。

#### Common-backbone lane

在同一 task block 内，`CB-PX-B0/B3/M0/MU` 使用 deterministic balanced cyclic order：

```text
order_seed = 2026080601
```

目标是减少 emulator drift、network drift 和 time-of-day effects。

#### Native systems

checkpoint loading 较重，因此按 model block 运行。Block order 由：

```text
order_seed = 2026080602
```

生成。

每个 arm 内 task order：

```text
SHA256(arm_id | task_seed)
```

映射为固定 permutation。

GUI-Owl 与 Mobile-Agent-v3.5 共享同一 checkpoint service，并在同一 block 中交替，以减少 model-server drift。

### 8.9 Model sampling seeds

对所有支持 seed 的 backends：

```text
model_seed = CRC32(arm_id | task_id | task_seed | attempt_id)
```

UI-Voyager 保留 official sampling parameters，但 seed 固定。

如某 native backend 不支持 deterministic seed：

- 记录 `sampling_seed_supported=false`；
- 不把单次 native trajectory 当作确定性复现；
- 仍可运行；
- 必须在 privilege/config table 披露。

### 8.10 Blinding

- official evaluator 不接收 arm ID；
- evaluator result 在 manual process annotation 完成前对 annotator 隐藏；
- exported annotation IDs 使用随机代号；
- annotator不知道 model/framework name；
- S2 全部 scientifically valid failures进行 first-broken-edge annotation；
- S3 对所有 successes、所有 finish claims、所有 loop≥3 cells、所有 feedback events 和 task-stratified 20% failure sample进行人工审计；
- 至少 20% annotations 双人独立标注；
- 所有 disagreement 和 `uncertain` 由第三次 blind adjudication 解决；
- 无明确 oracle 时不得强行标 wrong target。

- total model calls；
- calls / environment action；
- input tokens；

## 10.3 Canonical exact-action representation

每个 executed action 归一化为：

```text
(
  action_type,
  resolved_target_mode,
  round(x / screen_width, 3),
  round(y / screen_height, 3),
  visible_label_hash,
  normalized_text_hash,
```

- element-ID/index actions 必须在 execution time 解析为 bounds center；

- answer content 同样 hash；
- coordinate outside `[0,1]` 立即标 `CONTRACT_INVALID`；
- action canonicalizer 必须使用 fixtures 验证。

- maximum exact sequential run；
- exact repeat opportunities；
- exact repeats；
- cells with run ≥ 3；
- cells with run ≥ 10；
- wasted actions within exact runs；
- first exact-loop step。

```text
same action class
AND target-box IoU >= 0.90
AND same normalized text/direction
```

Exact 与 semantic loop 不得合并。

- +5 秒 screenshot；

- agent 不得看到 audit-only tree。

若 audit logger 没有 tree：

```text
pixel_only_no_effect
```

必须单独报告，不能与 strict metric pooling。

冻结指标：

- strict no-effect action rate；
- pixel-only no-effect rate；
- consecutive no-effect run；
- action class × no-effect；
- no-effect 后下一动作是否改变；
- no-effect 后 finish claim；
- no-effect 后 infeasible claim。

不得把 screenshot 不变自动称为“真实 action failure”，因为 hidden state 可能变化。允许术语是：

> no observable effect under the frozen audit channels

## 10.6 Feedback-to-next-action binding

Feedback event 包括系统显式产生的：

- `reobserve`；
- `retry`；
- `reflect`；
- `recover`；
- `replan`；
- `backtrack`；
- `progress warning`；
- `action failed`；
- `no effect`；
- `loop detected`。

分母：

```text
所有存在下一 executed action 的 feedback events
```

指标：

- exact next-action change rate；
- semantic next-action change rate；
- exact repeat rate；
- no-next-action rate；
- feedback 后第一个 effective action 的距离；
- feedback 后是否进入不同动作之间的 oscillation；
- feedback 类型 × outcome。

框架内部常规 thought 不自动算 feedback，只有明确指向 failure/recovery 的信息才算。

## 10.7 Wrong-target / destination metrics

只有满足以下条件的 decision 才进入 denominator：

1. frozen task parameters 确定 unique intended destination；
2. 当前屏幕同时可见至少两个 plausible candidates；
3. evaluator-side oracle 能把正确 destination 映射到 bounds/label；
4. agent observation 中没有直接泄漏 oracle 标记。

指标：

- wrong-target decisions / oracle-auditable decisions；
- first wrong-target step；
- source entity correct but destination wrong；
- correct text/value sent to wrong destination；
- repeated wrong-destination commitment；
- wrong target after feedback。

无 unique oracle 的 cell 标：

```text
wrong_target_not_auditable
```

不得由 annotator主观猜测。

## 10.8 Finish authority

Positive finish claims 包括：

- `done`；
- `success`；
- `completed`；
- terminal answer；
- 等价的 framework-specific success status。

冻结指标：

\[
\text{Evaluator-Rejected Finish Rate}
=
\frac{
\#(\text{positive finish claim}\land evaluator=0)
}{
\#(\text{positive finish claims})
}.
\]

另报告：

- premature finish before any state change；
- finish after no-effect run；
- finish after wrong target；
- negative infeasible declaration；
- evaluator success without explicit finish；
- answer content rejected by evaluator。

任何 controller 的自报 success 都不能覆盖 official evaluator。

## 10.9 First-broken-edge taxonomy

每条被人工审计的 trajectory 恰好赋一个 first broken edge：

```yaml
- evidence_acquisition
- destination_grounding
- action_contract
- action_execution_no_observable_effect
- feedback_policy_nonbinding
- loop_recovery
- goal_closure_finish_authority
- evaluator_mismatch
- environment_infrastructure
- unresolved
```

“first” 指最早足以使当前 trajectory 无法按原计划成功的可观察节点，不是事后最显眼的最后一个错误。

## 10.10 Predeclared primary process metrics

为避免事后从几十个 diagnostics 中挑结果，primary process metrics 固定为：

1. proportion of scientifically valid cells with exact-action run ≥ 3；
2. strict no-observable-effect action rate；
3. feedback-followed-by-exact-repeat rate；
4. evaluator-rejected finish rate；
5. oracle-auditable wrong-target rate；
6. model calls、tokens 和 wall time per native action budget。

其余为 secondary diagnostics。

## 11. Statistical Analysis

### 11.1 Unit of analysis

- task success：task-seed cell；
- process rates：action/event，但 inference 以 task class 为 cluster；
- 不得把 model calls、steps 或 feedback events 当作相互独立的 task samples；
- S2 是 exploratory；
- S3 是 seen-task-class fresh-instance confirmation。

### 11.2 Same-backbone comparisons

`CB-PX` 可报告：

- B3 vs M0；
- B3 vs B0；
- B3 vs MobileUse；
- M0 vs MobileUse。

但这些仍然是 controller-package comparisons，不是 isolated-module causal effects。

使用：

- paired success difference；
- exact paired permutation/sign test，以 task class 为 block；
- 10,000 次 task-cluster bootstrap；
- process metric difference 与 95% cluster-bootstrap interval；
- realized-resource difference。

### 11.3 GUI-Owl vs Mobile-Agent-v3.5

两者共享 checkpoint、processor 和 observation/action channel，因此这是外部 arms 中最强的 matched-checkpoint comparison。

仍不得简单说：

> multi-agent framework caused the success gain

因为它同时改变：

- prompts；
- number of calls；
- planning/progress/reflection structure；
- history construction；
- stopping behavior。

允许说：

> 在相同 GUI-Owl checkpoint 与 observation/action setting 下，完整 Mobile-Agent-v3.5 controller package 相对于 standalone GUI-Owl package 的 task/process/cost 差异为……

### 11.4 Native heterogeneous systems

ScaleCUA、UI-Voyager 与 X-PLUG systems：

- 只报告 descriptive end-to-end system results；
- 结果表必须同时显示 model size、checkpoint、sampling、observation privilege、calls、tokens、step budget 和 external tools；
- 禁止用单一 ranking 暗示 framework causality；
- 可以按 task class 报告 system coverage；
- 可以说某 system 在该 frozen configuration 下“achieved higher success”，不能说其 framework design“caused”该差异。

### 11.5 Confidence intervals and multiplicity

- success proportions：Wilson 95% CI；
- paired success：exact paired test；
- process metrics：task-cluster bootstrap 95% CI；
- process results以 effect size 和 interval 为主；
- 不把 secondary diagnostics 的 nominal \(p<0.05\) 作为主发现；
- 不对表现最好的 task subgroup进行未冻结的 confirmatory claim。

## 16. Exact Interpretation and Claim Rules

## 16.1 情况 A：task success 变为 non-zero

允许：

> “在 AndroidWorld commit `3e508885...`、冻结的 19 个 Hard task classes、指定 seeds、native action budgets 和所列 checkpoint/configuration 下，系统 X 完成了 \(x/n\) 个 scientifically valid cells。”

如果某现代 native system 成功而所有旧 RAVEN arms 仍为零，允许：

> “至少一个公开现代 native system 在该 frozen Hard subset 中逃离了旧 controller floor。”

`CB-PX` 内允许：

> “在相同 Qwen checkpoint、screenshot-only observation 和相同资源 ceiling 下，controller package X 相对 B3/M0 的 task/process/cost 差异为……”

GUI-Owl vs MA3.5 允许：

> “在相同 GUI-Owl checkpoint 下，standalone 与 multi-agent controller packages 表现不同。”

禁止：

- “ScaleCUA framework 导致了 improvement”；
- “multi-agent design caused the gain”；
- “memory caused the gain”；
- “复现了论文 71.6/81.0 headline”；
- “系统 X 在 AndroidWorld 上整体优于 Y”；
- “RAVEN-M 被现代方法全面证明过时”。

Native systems 的差异仍可能来自：

- model training；
- model scale；
- prompts；
- decoding；
- action grammar；
- history；
- calls；
- observation preprocessing；
- controller design。

## 16.2 情况 B：task success 仍为零，但 process metrics 改善

允许：

> “在 official task-success floor 未被跨越的情况下，系统 X 在预注册的 exact-loop/no-effect/feedback-binding/wrong-target/finish metric 上表现出较低或较高的发生率。”

推荐措辞：

> “X 改善了 measured process behavior，但这种改善不足以产生 official task-level utility。”

如果 loop 减少但 task success 仍为零：

> “Loop reduction 不是 task success 的充分条件；错误可能转移至 grounding、action effect 或 finish authority。”

如果 wrong-target 降低：

> “在 oracle-auditable decisions 中，X 更少选择错误 destination；该结果不等于完整 task success。”

如果 finish rejection 降低：

> “X 的 completion claims 与 official evaluator 更一致，但尚未证明提高 task completion。”

禁止：

- “process metric 改善说明方法有效”；
- “系统已经解决 AndroidWorld Hard”；
- “降低重复动作就是 causal recovery success”；
- “没有 task success 只是样本太小”；
- 在看到结果后把改善最大的 process metric 升级为 primary。

必须同时报告：

- 是否增加 calls/tokens/wall time；
- 是否将一种 failure 转化为另一种；
- 是否只在某一 task family 或 model 出现；
- confidence interval 是否跨过零。

## 16.3 情况 C：task success 与 process metrics 均不变

允许：

> “在冻结 configuration、budgets、task classes 和 seeds 下，系统 X 没有逃离该 Hard floor，也没有改变预注册的主要 process failure distribution。”

允许：

> “当前 Hard subset 可能主要受共享 environment/controller/grounding bottleneck 支配。”

禁止：

- “所有现代 mobile agents 都失败”；
- “系统之间等价”；
- “这些 framework 没有任何价值”；
- “AndroidWorld Hard 不可解”；
- “memory、verification 或 recovery 永远无效”；
- “零差异证明零因果效应”。

### 16.4 Mixed outcomes

若某些 arms 成功、某些 process metrics 变差：

- 必须报告 trade-off；
- 不得用 task success 隐藏成本或危险 process behavior；
- 不得只展示成功 task classes；
- 不得事后改变 arm tiers；
- 不得只确认表现最好的系统。

## 18. Final Verdict

# **GO_WITH_REVISIONS**

本 benchmark 在科学上值得执行，因为它直接解决旧研究最关键的证据缺口：

- 旧结果究竟是 RAVEN controller floor，还是整个公开 mobile-GUI ecosystem 在这些 Hard tasks 上都失败；
- 强 native checkpoints 是否能产生 non-zero official success；
- 即使 success 仍为零，process failure distribution 是否跨系统稳定；
- memory/verification/recovery hypotheses 是否至少有足够的自然 denominator 和跨系统 variance，值得未来另立项目研究。

但本授权是**conditional launch**：

```text
S0 pass
→ S1 non-Hard smoke pass
→ minimum launch set pass
→ model calls on Hard authorized
```

不得立即启动 Hard model calls。Codex 必须先完成本协议所列 v0.2 revisions、isolated environments、exact artifact pins、answer contract、privilege matrix 和 normalized logger。
