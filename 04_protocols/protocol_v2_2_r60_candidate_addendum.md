# Protocol v2.2 r60 Candidate Addendum

## Status and motivation

r60 is a local candidate derived from the immutable r59 H01 development
smoke. r59 showed that a generic Chrome button could initialize the ledger
before the task page existed. Inspection of the frozen AndroidWorld source
also established that `BrowserMultiply` generates one number on page load,
generates four more on clicks 1–4, and uses click 5 only to reveal the answer
form.

r60 corrects both the control-binding and sequence-semantics errors. It does
not change the frozen task, seed, variant, prompt templates, evaluator, action
budget, batch isolation, or acceptance criteria.

## Target-and-number co-binding

A numeric repeat ledger may initialize only when all of the following are true:

1. the proposed action hits exactly one visible, enabled, non-editable,
   non-commit control;
2. the finite-repeat goal binds that control through an explicit label or the
   preserved generic role-plus-task-application rule;
3. the goal explicitly requests collection and aggregation of displayed
   numbers;
4. the same pre-action task UI contains exactly one visible, non-clickable,
   non-editable pure numeric value in the bound application package;
5. the target action actually executes.

Thus Chrome setup controls such as `Accept & continue` cannot initialize the
ledger because no task numeric value coexists on that screen.

## Pre-action operand sampling

For the bounded H01 task shape, each actually executed target click samples the
unique numeric value visible immediately before that click. The sample ordinal
equals the executed click ordinal. This matches the task implementation:

- click 1 samples the load-time number;
- clicks 2–5 sample the values generated by clicks 1–4;
- click 5 may remove the number and reveal the form without creating another
  operand.

Equal values remain separate ordinal samples. Missing or ambiguous pre-action
numeric evidence leaves that ordinal absent; later values do not backfill or
renumber it.

## Two-axis completion

The ledger tracks independently:

- `executed_count`: actual target actions that reached
  `observe_transition`;
- `operands_complete`: exact numeric samples exist for every required ordinal.

`complete=true` means the requested action count executed. A deterministic
product may be stored when the operand set is complete, but it is ready for
post-repeat input only when both `complete=true` and
`operands_complete=true`. Before that joint state, the planner must finish the
remaining target actions and may not type the result early.

After joint completion, another exact target click is denied with
`TASK_REPEAT_COUNT_COMPLETE`; the repair must enter the verified deterministic
result into the visible task-bound field or take one reversible action toward
that field.

## Preserved boundaries

r60 preserves r58's repeated-action exception and every downstream denial.
It also preserves r59's rule that a proposal, rejection, repair, or
non-executed action cannot advance progress. The ledger never reads editable
text as an operand, never infers a disappeared fifth value, and never uses a
setup-page number or control from another package.

## Validation and launch boundary

Before any live r60 smoke:

- exact Chrome setup-button negative tests must pass;
- a replay-shaped `6, 2, 3, 9, 10 -> form` state-machine test must pass;
- missing/ambiguous ordinal and repeated-equal-value tests must pass;
- complete project tests and the protocol-v1 breadth seal must pass;
- exact source commit/tag, freeze hashes, a separate wrapper, and a zero-call
  preflight are required.

Local success alone does not authorize formal Gate F. r59 remains immutable.
