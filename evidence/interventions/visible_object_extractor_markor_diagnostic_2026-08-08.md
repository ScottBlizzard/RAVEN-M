# Markor 已观察页面的可见对象提取诊断

## 结论

本轮没有通过预注册资格门，因此不能据此实现在线的结构化记忆写入模块，也不能宣称方法有效。它仍然给出了一个重要的正反两面结果：在 Agent 实际打开 `my_expenses.txt` 或 `recipes.txt` 后，Qwen3-VL-32B 对自己明确看见的对象非常保守，13/13 次都输出合法 JSON，11 个预测对象全部正确，微平均精确率为 100%；但它只找回 21 个目标对象中的 11 个，微平均召回率为 52.38%，8 条轨迹中仅 3 条完整找齐全部目标。

这说明当前瓶颈不是“模型会不会凭空编造对象”，而是“长文档浏览是否覆盖了所有相关记录，以及被看见的记录能否被完整提取”。在覆盖不全时，把高精度的局部结果写进记忆仍会得到一份看似可信、实际缺项的对象集合；后续即使目标应用操作完全正确，也无法完成需要批量新增多个对象的任务。

## 冻结协议

- 性质：开发集污染的离线机制诊断，不是 held-out 效果实验。
- 对象：官方 Qwen3-VL-32B Hard 运行中，8 条确实进入 Markor `DocumentActivity` 且打开指定文件的轨迹。
- 输入：Agent 当时真正看到的 13 张 `before` 截图；不向模型提供隐藏的 `row_objects`。
- 评分真值：运行后才读取 AndroidWorld 初始化参数中的 21 个目标标识符。
- 输出：严格 JSON `{"objects":[{"identifier":"..."}]}`。
- 调用：固定模型 revision `0cfaf48183f594c314753d30a4c4974bc75f3ccb`，固定采样参数，每张截图一次调用，共 13 次；无重试、无事后调参。
- 资格门：13/13 合法输出、微平均精确率不低于 0.80、微平均召回率不低于 0.60、至少 4/8 条轨迹完整召回；四项必须全部通过。

## 机制解释

结果呈现的是一种“高精度、低覆盖”的失败。模型只在证据足够明确时输出，因此没有误报；然而长文档中的目标记录分散在不同位置，原始 Agent 并没有稳定翻遍文件并让每个目标完整出现在截图中。离线提取器只能忠实处理已经被观察到的画面，无法恢复从未进入视觉上下文的对象。也就是说，当前顺序应当是先解决可验证的文档覆盖，再讨论把提取对象保存为结构化记忆，最后才讨论跨应用绑定与写入。

该结论也限制了下一步：不能为了越过 60% 门槛在同一批 13 张截图上反复改提示词；允许的后续工作是对已有轨迹做零生成的“源应用 -> 正确文件 -> 覆盖目标 -> 进入目标应用 -> 正确写入”漏斗审计，或者另行预注册新的在线探索/翻页实验。
